# 测试充分性指标的效度评估协议

**版本**：v1　**日期**：2026-10-16　**产出**：ClawsGO Science Agent
**数据来源**：Defects4J，7 个项目、70 个独立缺陷版本、219 个测试子集实例（持续扩充中）

---

## 为什么要这份协议

大量研究在问同一个问题：**"指标 X 能否预测测试套件的缺陷检测能力？"** 典型做法是取若干开源项目、若干缺陷版本，计算指标与检错能力的相关性，报告相关系数或回归 R²。

我们在 Defects4J 上完整走过这条流程，得到了一个看起来很好的结果：

> 把断言层面的行为匹配特征加入模型，交叉验证 R² 从 0.561 提升到 0.628，检验高度显著（ΔR²=+0.089, p<0.0001）。

**这个结论是错的。** 追加三项诊断后，同一个数据集给出了相反的答案：控制项目身份后，加入这些特征使样本外预测从 0.567 降到 0.553。

本协议把这三项诊断形式化，供后续研究复用。

---

## 诊断一：伪重复 —— 先算有效样本量

### 问题

分析单位是"套件实例"，但实例并非独立：同一缺陷版本的多个子集共享同一批测试源码。把样本量堆在"每个缺陷多个子集"上，对统计推断几乎没有贡献。

### 我们数据中的实况

| 口径 | 数量 |
|---|---|
| 名义实例数 | 106 |
| **独立基准版本数** | **13** |

13 个独立观测却按 106 个计算显著性——这是伪重复。

### 诊断方法

```python
n_nominal  = len(df)                                  # 实例数
n_effective = df.groupby(['project','bug']).ngroups   # 独立单元数
```

**若 `n_effective / n_nominal < 0.5`，必须改用聚类稳健标准误，或直接把分析单位降到独立版本层级。**

### 修复

- 报告并聚类：`fit(cov_type="cluster", cov_kwds={"groups": df["bugkey"]})`
- 设计上：**增加独立缺陷版本数，而非每版本的重复次数**

我们据此把设计从"13 个版本 × 8 个子集"改为"70+ 个版本 × 2 个子集"。

---

## 诊断二：项目指纹 —— 特征是否只是在标识项目

### 问题

任何具有**项目级风格**的特征都会"预测"检出率，因为它首先在识别项目。项目之间在测试风格、代码规模、缺陷构成上差异巨大，这些差异会被误读为指标的效力。

### 我们数据中的实况

用随机森林仅凭各特征集预测实例属于哪个项目（5 折交叉验证）：

| 特征集 | 准确率 |
|---|---|
| 仅行为匹配特征（断言类型占比等） | **0.863** |
| 仅传统指标（规模 + 覆盖率 + 变异分数） | 0.795 |
| 全部特征 | 0.923 |
| 随机基线（7 个项目） | 0.143 |

**同样的问题对传统指标也成立**——覆盖率类特征也能以 79.5% 识别项目。

### 诊断方法

```python
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import cross_val_score
acc = cross_val_score(RandomForestClassifier(n_estimators=300, random_state=0),
                      df[feature_cols].values, df["project"], cv=5).mean()
baseline = 1 / df["project"].nunique()
```

**判据**：若 `acc` 显著高于基线（经验上 >2 倍基线即需警惕），该特征集在跨项目汇总分析中不可信。

### 修复

见诊断三。

## 诊断三：项目固定效应 —— 项目内的效应才是真的

### 方法

组内去均值（within transformation），剔除项目间差异后重新检验：

```python
dm = df[cols] - df.groupby("project")[cols].transform("mean")
```

或等价的回归形式：加入项目虚拟变量，并按独立缺陷版本聚类标准误。

### 我们数据中的实况

**交叉验证 R² 的对照（这一步最能说明问题）**：

| 模型 | 无项目固定效应 | 含项目固定效应 |
|---|---|---|
| 仅套件规模 | 0.237 | 0.567 |
| 规模 + 覆盖率 + 变异分数 | 0.417 | **0.618（最优）** |
| 规模 + 行为匹配 | 0.262 | 0.553 |
| 完整 | **0.435（看似最优）** | 0.603（反而下降） |

**无项目控制时给出错误的模型排序**：完整模型看似最优；加入项目控制后，经典指标组合最优，行为匹配特征反而有害。

> **稳健性复查（2026-10-16 追加）**：上表的排序在点估计上稳定，但**差值本身不可分辨**，须如实报告。
> 按缺陷版本分组重采样 200 次（5 折分组交叉验证、含项目控制）：
> $$\Delta R^2(\text{完整} - \text{规模+覆盖+变异}) = -0.038,\ 95\%\ \text{CI} = [-0.131, +0.026]$$
> 90% 的自助样本跨零。改用留一版本交叉验证，同一差值变为 $$+0.043$$（**符号相反**）。
> 因此可下的结论只有一条：**该增量在 n=70 个独立版本下不可识别**，而非"行为匹配特征有害"。
> 这本身是本协议要传达的第三件事——**多数此类研究报告的增量 R² 量级（0.05 上下）远低于其设计的分辨力**。

**项目内相关：一个显著效应消失**：

| 特征 | 整体 ρ | 项目内 ρ | p |
|---|---|---|---|
| 套件规模 | +0.575 | **+0.728** | <0.001 |
| 覆盖率 | +0.609 | **+0.725** | <0.001 |
| 变异分数 | +0.069 | +0.295 | <0.001 |
| 每方法断言数 | −0.003 | +0.034 | 0.620 |
| **强断言占比** | −0.239 | **−0.075** | **0.266** |
| 断言涉及调用数 | −0.049 | −0.173 | 0.010 |

"强断言占比越高、检出越少"在跨项目下 ρ=−0.254（p=0.033）显著，项目内降到 −0.075 且不显著。**该效应是项目差异造成的假象。**

## 推荐的评估协议

按顺序执行，任一步不过关就停下修设计：

### 步骤 1：确定分析单位与有效样本量

- 结果变量须能从**独立于被测套件**的来源获得。本项目用 Defects4J 的触发测试元数据计算"检出本项目多少个真实缺陷"，无需执行测试。
- 报告 `n_effective`。若远小于 `n_nominal`，按独立单元聚类或降到该层级分析。

### 步骤 2：构造对照套件（若需要控制规模）

若研究问题是"控制规模后指标是否还有效"，必须能构造规模可比、构成不同的套件。本项目的方法：把不参与子集的测试源码移出测试目录，只让子集参与构建。

### 步骤 3：项目判别力体检

对每个候选特征集跑诊断二。**判别力接近或超过基线数倍的特征集，必须在跨项目分析中控制项目身份，或改为项目内分析。**

### 步骤 4：报告两套结果

- **跨项目（pooled）**：便于与既有文献对照；
- **项目内（fixed effects）**：作为结论的依据。

**若两者结论不一致，以项目内结果为准，并把不一致本身作为发现报告。**

### 步骤 5：样本外验证

用 K 折交叉验证而非样本内 R² 做模型比较。我们的数据中，样本内 R² 的模型排序与 CV R² 的排序在含项目控制时并不一致。

**并且必须给出该比较的分辨力。** 只报告点估计的 ΔR² 会让读者以为被测出了效应，而实际上方案之间的差别可能小于噪声：

| 独立版本数 | ΔR² 的 95% 区间宽度（本项目实测） |
|---|---|
| 15 | ≈ 4.1 |
| 30 | ≈ 2.2 |
| 50 | ≈ 0.7 |
| 70 | 0.16 – 0.47（随交叉验证方案变化） |

**含义**：若目标效应量级是 ΔR²≈0.05，**本领域常见的 10–30 个版本的样本量在原理上无法分辨该效应**。论文若要主张"指标 X 有增量价值"，必须先说明其设计能分辨多大的效应；否则该主张不可证伪。

### 步骤 6：报告诊断结果

论文中明确给出：有效样本量、特征的项目判别力、是否有项目固定效应下的复现。这三项本身就是可复现性的一部分。

## 陷阱清单（本项目实测踩到的）

| 陷阱 | 症状 | 后果 |
|---|---|---|
| **伪重复** | 名义 n 远大于独立单元数 | 高估显著性 |
| **项目指纹** | 特征能高准确率识别项目 | 跨项目结论不可信 |
| **未报告有效样本量** | 只报告实例数 | 读者无法判断可靠性 |
| **只看样本内 R²** | 高维模型 R² 虚高 | 选错模型 |
| **混淆"语法层"与"语义层"代理** | 用断言类型占比代表行为匹配 | 结论无法外推到原假设 |
| **工具默认作用范围** | `defects4j coverage` 默认只测被修改的那一个类 | 指标语义塌缩（实测差 30 倍） |
| **在缺陷版本上跑变异测试** | 失败测试使构建中止 | 数据缺失；且引入 Clean Program Assumption |

---

## 本协议的适用边界

1. **固定效应会消除项目层面的真实效应**。若某指标的真实作用恰在项目层面（如"某类项目的套件普遍更强"），固定效应会把它一并抹去。因此本协议的结论表述应为"**项目内**该指标是否有效"，而非"该指标是否有效"。
2. **协议的三个诊断都不需要执行被测套件**（本项目的结果变量由元数据算出），因此计算成本低，适合作为投稿前的常规体检。
3. **跨基准的推广未验证**。本项目仅在 Defects4J 上实施；其他基准（如 BugsInPy）是否重现"项目指纹"现象，需另行检验。
